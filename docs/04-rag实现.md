# RAG 实现

## 为什么需要 RAG

模型的知识有截止时间，也不知道你的私有资料。RAG（检索增强生成）的思路是：先把资料存成向量，提问时检索出最相关的几段，把它们塞进上下文再让模型回答。这样答案有据可查，也避免了把整本资料塞进 prompt 的高昂成本。

## 文档切块

原始文档不能整篇向量化。一篇长文压成一个向量，语义被平均掉，检索精度会很差。所以要先切块：knowledge.py 按 markdown 标题分节，再把同一节里的段落累加，单块上限约 420 字符。

每个块在开头拼上它所属的小节标题。这一步很关键，因为单独一句「响应慢可以加缓存」看不出在讲什么，加上标题变成「【性能优化】响应慢可以加缓存」之后，向量里的语义信息就完整了。这叫块级上下文补全。

## 向量化与缓存

调用智谱 embedding-3 把文本转成 2048 维向量。每段文本的向量只和文本内容有关，所以可以缓存：用文本的哈希值做键，内容没变就直接复用旧向量，不重复调用接口。

缓存文件在 .cache/kb_vectors.npz，存了块 id、内容哈希和向量矩阵。启动时先比对哈希，只把新增或改动过的块送去向量化。改一篇文档只重算那一篇的块，其余全部命中缓存。

这个设计解决的是真实痛点：文档一多，每次启动都全量嵌入要等十几秒还花钱，而实际上大部分内容根本没变。

## 检索

检索时把问题也向量化，然后算余弦相似度取 top-k。实现上用矩阵乘法一次性算出所有块的相似度，再按分数排序取前几。余弦相似度只关心方向不关心长度，所以要先把向量归一化，之后点积就等于余弦值。

默认返回 top 3 块，每块带上来源文件名、小节标题和相似度分数。带上来源不只是为了好看，而是让用户能自己去核对原文，这是抑制幻觉的最后一层保障。
