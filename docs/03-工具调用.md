# 工具调用

## 协议本身

工具调用不是模型真的执行了什么，模型只输出一段结构化的调用意图：函数名加 JSON 参数。真正执行发生在本地代码里。完整流程是三步：把工具的 JSON Schema 随请求一起发给模型，模型返回 tool_calls，本地按名字查表执行再把结果回传。

Schema 里最重要的三样是 name（函数名）、description（什么时候该用它）、parameters（JSON Schema 描述的入参）。description 写得好不好，直接决定模型会不会在该用的时候用、参数给得对不对。

## 注册表设计

tools.py 里有两个东西：TOOLS 是给模型看的说明书列表，TOOL_FUNCS 是函数名到真实函数的字典。Agent 拿到 tool_calls 后，用函数名字符串在 TOOL_FUNCS 里查表，取到函数对象再执行。

这种「字符串到函数」的映射是工具系统的本质。新增一个工具只需要改两个地方：写函数，加进 TOOLS 和 TOOL_FUNCS。Agent 的循环代码一行都不用动，这就是开闭原则在这里的具体体现。

## 当前内置的三个工具

calculate 用 eval 计算数学表达式，适合验证多步推理里「算一下」这类需求。get_current_time 返回当前时间，用来验证模型会不会主动获取实时信息。search_docs 调用知识库检索，是整个 RAG 能力的入口。

## 异常处理

最早的实现是直接调用 TOOL_FUNCS[name](**args)，工具内部一旦抛异常，整个对话就崩了。现在做了两层兜底：函数名不存在时返回「没有这个工具」，工具执行抛异常时把错误信息转成字符串回传给模型。

让模型看到错误比让程序崩溃更好，因为它往往能换个参数重试，或者把失败原因转述给用户。这也是为什么工具返回统一转成字符串：tool 消息的 content 必须是文本。
