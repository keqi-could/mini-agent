# 常见问题

## 怎么防止模型胡说

三层防线。第一层是 system prompt，明确要求回答只能基于检索到的内容，资料不足时直接说知识库中没有相关信息。第二层是检索结果带来源，模型能看到自己引用的是哪一段。第三层是 max_steps 与工具异常兜底，避免它在错误路径上反复绕。

测试方法是问一个知识库里没有的问题，比如「这个项目支持哪些编程语言以外的语言」，观察它是老实说不知道，还是编造一份语言列表。

## 为什么不用 LangChain

框架能省掉样板代码，但也把关键机制藏起来了。面试时被问「工具调用是怎么实现的」，答「调了一个 API」是没用的，能说清楚 JSON Schema 怎么描述、tool_calls 怎么回填、为什么要带 tool_call_id，才是自己的东西。

这个项目的取舍是：该手写的手写，把循环、检索、缓存这些核心逻辑全部摊开；该用库的用库，比如 HTTP 客户端和界面渲染不重复造轮子。

## 多轮记忆是怎么实现的

记忆不是模型自带的。模型本身是无状态的，每次请求都是独立的。所谓记忆，就是把之前的对话历史一直攒在 messages 列表里，每次请求都把整个列表重新发给它。

所以 Agent 实例必须活到会话结束，在 Streamlit 里就挂在 st.session_state 上。因为 Streamlit 每次交互都会重跑整个脚本，局部变量会被清空，只有 session_state 里的对象能跨请求存活。

## 上下文会无限增长吗

会，现在没有做截断。消息条数越多，每次请求的 token 就越多，成本和延迟都会上升。合理的做法是滑动窗口保留最近若干轮，或者把早期对话做摘要。

这是已知的限制，也是下一步要改的点。承认边界比假装完美更可信。

## 向量缓存在什么时候失效

缓存以内容哈希为键，文本改了就重算，没改就一直命中。换向量模型时整个缓存都要失效，因为不同模型的向量空间不通用，混用会导致检索结果完全错乱。缓存文件里记录了模型名，比对不上就整体重建。
