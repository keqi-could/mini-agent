# 常见问题

## 怎么防止模型胡说

三层防线。第一层是 system prompt，明确要求回答只能基于检索到的内容，资料不足时直接说知识库中没有相关信息。第二层是检索结果带来源，模型能看到自己引用的是哪一段。第三层是 max_steps 与工具异常兜底，避免它在错误路径上反复绕。

测试方法是问一个知识库里没有的问题，比如「这个项目支持哪些编程语言以外的语言」，观察它是老实说不知道，还是编造一份语言列表。

## 为什么不用 LangChain

框架能省掉样板代码，但也把关键机制藏起来了。面试时被问「工具调用是怎么实现的」，答「调了一个 API」是没用的，能说清楚 JSON Schema 怎么描述、tool_calls 怎么回填、为什么要带 tool_call_id，才是自己的东西。

这个项目的取舍是：该手写的手写，把循环、检索、缓存这些核心逻辑全部摊开；该用库的用库，比如 HTTP 客户端和界面渲染不重复造轮子。

## 多轮记忆是怎么实现的

记忆不是模型自带的。模型本身是无状态的，每次请求都是独立的。所谓记忆，就是把之前的对话历史一直攒在 messages 列表里，每次请求都把整个列表重新发给它。

所以 Agent 实例必须活到会话结束，在 Streamlit 里就挂在 st.session_state 上。因为 Streamlit 每次交互都会重跑整个脚本，局部变量会被清空，只有 session_state 里的对象能跨请求存活。

## 上下文会无限增长吗

不会。Agent 默认只保留最近 6 轮对话原文，超出之后最老的一轮会被丢掉，丢弃之前先压成一段不超过 120 字的摘要，放在 system 消息之后作为背景。

这样上下文规模被钉在「system + 摘要 + N 轮原文」，聊一百轮和聊十轮的成本差不多。

## 为什么按整轮丢弃

一条用户消息后面可能跟着 assistant 的 tool_calls 消息和若干条 tool 回传消息，它们靠 tool_call_id 一一对应。如果只丢掉其中一条，接口会因为找不到对应调用而返回 400。

所以裁剪单位是「轮」而不是「条」：从某条 user 消息开始，一直丢到下一条 user 消息之前，保证协议完整。也正因为如此，messages 里不存 system 消息，它由 _context 在请求前临时拼上，避免裁剪时把 system 一起算进轮次里。

## 摘要失败会怎样

摘要本身也是一次模型调用，可能超时或报错。这时退化成朴素兜底：直接截取被丢弃内容的后 300 字当摘要。

宁可摘要糙一点，也不能因为压缩动作本身失败而让整轮对话崩掉。压缩是优化手段，不在关键路径上。

## 向量缓存在什么时候失效

缓存以内容哈希为键，文本改了就重算，没改就一直命中。换向量模型时整个缓存都要失效，因为不同模型的向量空间不通用，混用会导致检索结果完全错乱。缓存文件里记录了模型名，比对不上就整体重建。

## 相似度阈值是怎么定的

不是拍脑袋定的数字。仓库里有一个 eval_retrieval.py，固定了一组真实问题和一组知识库完全覆盖不到的无关问题，跑一遍输出命中率、MRR 和无关问题的拒绝率。

阈值取在两组分数的空档中间：相关问题的最低分和无关问题的最高分之间。这个做法比凭感觉设一个 0.5 更可靠，因为阈值和语料是绑定的，换一套文档分档就会移动。

但要清楚它的局限：评测样本数量有限，空档往往很窄，语料一扩充就可能失效。所以文档改动之后要重跑评测，而不是把某个数字当成常数。
